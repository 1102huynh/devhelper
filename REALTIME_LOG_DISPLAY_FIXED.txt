🐛 VẤN ĐỀ TRƯỚC ĐÂY

PROBLEM 1: Backend Clear Logs Between Suites
  ❌ Mỗi lần runTest() được gọi → Backend clear log
  ❌ Khi chạy sequential, logs của suite trước bị mất
  ❌ User không thể xem lại logs của tất cả suites

PROBLEM 2: Frontend Incremental Append Logic
  ❌ Frontend cố append incremental nhưng backend clear log
  ❌ Conflict giữa frontend tracking và backend clearing
  ❌ Logs bị mất hoặc duplicate

✅ GIẢI PHÁP ĐÃ IMPLEMENT
═══════════════════════════════════════════════════════════════════════════

BACKEND CHANGES:
────────────────────────────────────────────────────────────────────────

1. Keep Logs Across Sequential Runs
   ────────────────────────────────────────────────────────────────────
   OLD CODE:
   ```java
   testLogs.put(projectId, new StringBuilder());  // Clear every time
   ```

   NEW CODE:
   ```java
   // Only initialize if not exists (keep existing logs)
   testLogs.putIfAbsent(projectId, new StringBuilder());
   ```

   BENEFIT:
   ✓ Logs accumulate across multiple suite runs
   ✓ User can see complete history of all suites
   ✓ No data loss between sequential runs

2. Add Clear Log Method
   ────────────────────────────────────────────────────────────────────
   ```java
   public void clearTestLog(String projectPath) {
       testLogs.put(projectPath, new StringBuilder());
   }
   ```

   USAGE:
   → Call this ONLY when user clicks "Start Execution"
   → Clears old logs before starting new test session
   → Manual control over when to clear

3. New API Endpoint
   ────────────────────────────────────────────────────────────────────
   ```java
   @PostMapping("/clear-log")
   public ResponseEntity<Void> clearLog(@RequestParam String projectPath) {
       testService.clearTestLog(projectPath);
       return ResponseEntity.ok().build();
   }
   ```

FRONTEND CHANGES:
────────────────────────────────────────────────────────────────────────

1. Clear Log on Start
   ────────────────────────────────────────────────────────────────────
   ```typescript
   const runTest = async () => {
       // Clear log on backend before starting
       await fetch(`${API_BASE}/test/clear-log?projectPath=...`, {
           method: 'POST'
       })

       // Then start running tests
   }
   ```

2. Simplified Polling Logic
   ────────────────────────────────────────────────────────────────────
   OLD (Complex):
   ```typescript
   let lastLogLength = 0
   const newLog = backendLog.substring(lastLogLength)
   setTestLog(prev => prev + newLog)  // Append incremental
   lastLogLength = backendLog.length
   ```

   NEW (Simple):
   ```typescript
   const fullLog = await fetch(...).text()
   setTestLog(fullLog)  // Just set the full log
   ```

   BENEFIT:
   ✓ Simpler code
   ✓ Backend manages all log accumulation
   ✓ Frontend just displays what backend has
   ✓ Always in sync

3. Remove Frontend Log Manipulation
   ────────────────────────────────────────────────────────────────────
   REMOVED:
   ```typescript
   setTestLog('=== Sequential Test Execution ===\n')
   setTestLog(prev => prev + `Suite ${i+1}/${total}\n`)
   setTestLog(prev => prev + `✓ Suite completed\n`)
   ```

   REASON:
   → Backend logs everything already
   → Frontend adding text creates confusion
   → Let backend be single source of truth

        Backend: Returns FULL accumulated log
        ↓
        Frontend: setTestLog(fullLog)  ← Display all
        ↓
        User: Sees REAL-TIME logs in terminal
        ↓
    Backend: Process completes
        ↓
    Frontend: Move to next suite
        ↓
Frontend: All suites completed
        ↓
User: Can see ALL logs from ALL suites in terminal

📊 POLLING MECHANISM
═══════════════════════════════════════════════════════════════════════════

How It Works:

1. Frontend polls every 1 second
2. GET /api/test/log?projectPath=...
3. Backend returns FULL accumulated log
4. Frontend displays in terminal UI
5. User sees updates in real-time

Performance:
  - Polling frequency: 1 second
  - Network: ~1 KB - 100 KB per request (log size)
  - Efficient: Only during test execution
  - Stops: When test completes

Why 1 Second?
  ✓ Fast enough to feel real-time
  ✓ Not too aggressive on network
  ✓ Standard polling interval
  ✗ Could use WebSocket for true push (future enhancement)
